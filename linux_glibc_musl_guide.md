# Совместимость бинарных файлов Linux: glibc, musl, статическая линковка и архитектуры

Это руководство объединяет ключевые аспекты сборки, проверки и переносимости исполняемых файлов (бинарников) в Linux на примере языков Rust и Go.

---

## 1. Проблема версий glibc в Rust и способы её решения

Ошибка вида `/usr/lib/libm.so.6: version 'GLIBC_2.43' not found` возникает, когда программа скомпилирована на системе с новой версией библиотеки `glibc` (например, Arch Linux), а запускается на системе с более старой версией (например, Debian или Ubuntu).

### Вариант А: Статическая сборка с `musl` (Самый простой способ)
Программа встраивает в себя альтернативную стандартную библиотеку `musl` и перестаёт зависеть от системной `glibc`.
```bash
rustup target add x86_64-unknown-linux-musl
cargo build --release --target x86_64-unknown-linux-musl
```
* **Плюсы:** Работает на любом дистрибутиве Linux (включая Alpine).
* **Минусы:** Возможны сложности при сборке сложных C-зависимостей (OpenSSL, графика).

### Вариант Б: Сборка под конкретную версию glibc через `cargo-zigbuild`
Инструмент `cargo-zigbuild` использует компилятор Zig в качестве линковщика, позволяя указать минимальную целевую версию `glibc`.
```bash
cargo install cargo-zigbuild
cargo zigbuild --release --target x86_64-unknown-linux-gnu.2.31
```
* **Плюсы:** Отлично работает с C-зависимостями и сохраняет производительность `glibc`.

### Вариант В: Сборка в контейнерах (`cross` или Docker)
Для максимальной совместимости с системными библиотеками проект собирают внутри старого окружения (например, образы `manylinux` или утилита `cross`).
```bash
cargo install cross
cross build --release --target x86_64-unknown-linux-gnu
```

## 2. Как проверить требования бинарного файла

Чтобы узнать, какую минимальную версию `glibc` требует готовый файл и как он слинкован, используются стандартные утилиты Linux (`binutils`).

### Проверка минимальной версии glibc
Максимальное число в конце отсортированного списка указывает на минимально необходимую версию `glibc`:
```bash
# Через objdump (самый точный способ)
objdump -T ./имя_бинарника | grep -oE 'GLIBC_[0-9.]+' | sort -Vu

# Через readelf
readelf -V ./имя_бинарника | grep -oE 'GLIBC_[0-9.]+' | sort -Vu

# Через strings (если не установлены инструменты разработчика)
strings ./имя_бинарника | grep -oE '^GLIBC_[0-9.]+$' | sort -Vu
```

### Проверка статической линковки и архитектуры
* **Команда `ldd ./имя_бинарника`:** для статического файла выведет `not a dynamic executable`.
* **Команда `objdump -T ./имя_бинарника`:** для статического файла выведет `не динамический объект` (`not a dynamic object`).
* **Команда `file ./имя_бинарника`:** покажет и процессорную архитектуру, и тип линковки (например, `ELF 64-bit LSB executable, x86-64, ..., statically linked`).

## 3. Сравнение подходов: свежий glibc, старый glibc и musl

| Параметр | Свежий glibc | Старый glibc (например, 2.31) | Статический musl |
| :--- | :--- | :--- | :--- |
| **Производительность памяти** | Максимальная | Максимальная | Ниже в многопоточной среде |
| **Размер бинарника** | Небольшой | Небольшой | Больше (включает саму библиотеку) |
| **Переносимость** | Только новые ОС | Почти все актуальные ОС | Любой Linux (даже Alpine) |
| **C-зависимости (FFI)** | Работают из коробки | Работают из коробки | Часто требуют сложной настройки |
| **Обновления безопасности** | Обновляется вместе с ОС | Обновляется вместе с ОС | Требует пересборки программы |

* **Компромиссы старого glibc:** Почти отсутствуют. Программа на целевом сервере всё равно использует установленную там системную библиотеку и получает системные патчи безопасности.
* **Компромиссы musl:** Стандартный аллокатор памяти в `musl` медленнее работает при большом количестве потоков (в Rust это решается подключением `mimalloc` или `jemallocator`). Также статический бинарник не может динамически загружать внешние плагины (`.so`).

## 4. Как обстоят дела в Go

* **Чистый Go (`CGO_ENABLED=0`):** Проблемы с `glibc` нет. Runtime Go обращается напрямую к ядру Linux через системные вызовы и использует собственный сетевой стек.
  ```bash
  CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -o app
  ```
* **Go с C-зависимостями (`CGO_ENABLED=1`):** При использовании `cgo` (например, `go-sqlite3`) бинарник динамически привязывается к `glibc` сборочной машины. Решается это так же, как в Rust — указанием Zig в качестве C-компилятора:
  ```bash
  CGO_ENABLED=1 CC="zig cc -target x86_64-linux-gnu.2.31" go build -o app
  ```

## 5. Статическая линковка и процессорные архитектуры (x86_64, i386, aarch64)

Статическая линковка (`statically linked`) решает **только** проблему зависимости от системных библиотек (`glibc`), но **не делает** файл универсальным для разных процессоров.

* **Привязка к набору инструкций:** Бинарник, собранный под `x86_64`, не запустится на `aarch64` (ARM) или `i386` (система выдаст ошибку `Exec format error`).
* **Обратная совместимость x86:** Статический файл для 32-битной архитектуры `i386` сможет работать на 64-битных процессорах `x86_64` (если в ядре Linux включена поддержка 32-битных приложений). Обратное невозможно.
* **Отдельные сборки под ARM:** Для процессоров `aarch64` (Raspberry Pi, AWS Graviton и др.) всегда требуется отдельная кросс-компиляция (например, под таргет `aarch64-unknown-linux-musl`).
